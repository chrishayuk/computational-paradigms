# Independent classification notes — SWI-Prolog, 1C, P09–P11

Classifier: Codex (GPT-6 family), independent of the implementation author and the other classifier. Only the supplied repository and the designated output directory were used. No Prolog program, harness, system, or repository checking tool was executed. The Python scripts beside this file read data and check the classification; they do not import repository code.

`swi-prolog.json` is the classification. `classify.py` reconstructs it from the allowlisted token streams and records. `validate_classification.py` checks every frozen index, every behaviour stage/computation/reading, all target log jobs, and the recorded program hashes. `inventory.json` lists the 210 records examined; `validation.json` records the checks and totals. Paths in the JSON are relative to the supplied repository root, except references to these output artifacts.

## Coverage and conventions

The batch index contains 32 distinct texts, shared by 65 program paths. All are covered once under the index's first path. The corresponding frozen token sequences were compared for every alias. No configuration changes the classes of the tokens in a shared text: session's additional supporting module is separately loaded and does not change the constructs in those programs. No source text was re-tokenized.

There are 70 behaviour records and 140 measurement records, matching all 210 jobs in the 15 P09/P10/P11 batch-1C logs. There are no named program variants, `*.INVALID.json` records, or `raw-rerun-m2` records for these three problems in this snapshot; the permitted rerun log contains no target job. Its other problems were not used. No P08 text is in this batch, so `late_definition` is empty.

The 160 outcome entries are per stage, attempt and computation, with a further entry for the second reading of each of the five P09d runs. P09d's instance remains `P09d`; `reading` identifies finite or stream. Null representation means that no solution representation was reported. A finitely exhausted empty answer set is explicit, whereas a budget or error without an answer is `none reported`. P11's any-one rule is applied at provisional stages too.

Observations retain the small answers verbatim. The very large open-list observations of plain/tabling P09d are referenced by exact record field, with their character count, SHA-256 and an excerpt; their verbatim source was not loaded into the classification document. The observations record no Total binding there. Storage figures are explicitly sourced to their separate storage run and do not replace behaviour classifications.

## Constructs that required judgement

* **emit overrides the generic H list.** The SWI harness README section 12 calls its stub H, but P11 explicitly says emit and commit are problem tokens. I apply the problem-specific rule: each emit call, including its preceding separator, is P. Otherwise the experiment would charge the central problem operation to the harness. Fixed heads, unknown-name facts and `h_commitment/1` remain H.
* **Nested delay wrappers.** `freeze`/`when`, their waiting conditions and closing punctuation are C. The delayed producer, arithmetic, or comparison inside is classified independently (rules 1 and 10). Thus `constraints/P09c.pl` 49–52 and 60 are C, while 53–59 are the P recursive gen call. These are scheduling annotations, without a moved producer conjunct or a new generator case. Tabling directives are C. Imports of clpfd are C configuration declarations; relational arithmetic calls are P.
* **Arithmetic mode evaluators.** The extra sum/diff and sum_known/diff_known clause heads in P09e are R: the problem gives primitive arithmetic relations, not these additional mode-dispatch cases. Mode tests and cuts are C under rules 1–2, including cuts whose operational commitment can lose directions. Each arithmetic evaluator expression is P under rules 8 and 10: it computes a place of the same primitive integer relation. These predicates take all three places; they are not separately written direction-specific APIs to which rule 14 would assign an entire function. For example, `coroutines/P09e.pl` 63–71 is an R helper head, 72–82 its C dispatch, and 83–88 the P addition. Rule 19's evaluator distinction supports this separation, although its opening language speaks specifically of imperative programs; here the mode-dispatch bodies themselves use directional imperative evaluation. That scope is an ambiguity in the rules.
* **Standing versus snapshot arithmetic.** In plain/coroutines P10b, `D is K*B` is R under rule 8: stage 1 asks for an unvalued standing relation. The analogous CLPFD `#=` is P. Relative replacement and the P10c snapshot compute in the given direction and are P (rules 3 and 8). Native database edits implementing named quantity replacement are P, without version indexing. Presence dispatch in queries is C; the query's binding/value-reading goal is P.
* **Retractable relation holder.** P10d's new `held/2` wrapper and the query that applies stored comparisons are R. A comparison inside the wrapper is still P; coroutines' inner freeze is C. I treat this as a small encoding of this problem's single retractable comparison, using native database update, rather than an added general constraint engine (S). It provides no general propagation, work queue, scheduler, or unification. The R/S boundary would be clearer if rule 19 explicitly addressed native Prolog databases used to retain callable relations. All ranges are in the JSON.
* **Commit replay decoder.** `committed_value/2`, its call and decoding goals are R extra protocol representation. They turn a textual replayed answer into the problem's equality; they compute something the report depends on and are not an output-only adapter under rule 13. `h_commitment/1` alone is H. The conditional around first pose versus replay is C, with its `->` connective C under rule 10. For `constraints/P11d.pl`, these include C punctuation at 66, 71, 78–80, H 67–70, and the R helper 117–151.
* **Punctuation and declarations.** Clause-head introducers and the final full stop take the enclosing clause class (rule 10); therefore a stage/query clause's head and full stop are H, while its body is split. Separators take the following construct's class (rule 20). Dynamic declarations are C under rule 11: they make absent database predicates fail rather than raise an undefined-predicate error, as the P10 queries/withdrawals need. The rule's explicit wording applies beyond P08, although its examples emphasize that problem.

No move or omission of a problem case/conjunct was found. Arithmetic decomposition through N1 and the partial sum is the primitive arithmetic convention, not an efficiency accumulator. `member/2` and `memberchk/2` read the actual stage entries or enumerate the given pick facts (rules 6, 7 and 9); they do not introduce an unstated value domain.

External mechanisms present in these texts include clpfd, coroutines' freeze/when/dif and tabling. Outside the listed plain core, the programs also use member/memberchk, forall, retractall, use_module and term_string. Their call/declaration tokens are counted by role, rather than as S. None is silently credited as part of plain's enumerated core.

## Supporting code and its counting limit

No target program supplies S code. Session loads the phase-4 `S/session-wait.pl` mechanism for every run, but these programs never invoke an undefined procedure, so the hook is dormant. Each session program lists it in `s_mechanisms`; other programs explicitly list no mechanism.

There is no frozen token TSV for that separately loaded module anywhere in the permitted tokens directory. Consequently its independent S/H split is **unavailable**, represented by null, not an invented zero or a re-tokenization. The phase-4 declaration of 158 total lexical tokens is retained separately as `phase_4_declared_total_tokens`; it is not my independent S count. Its `h_wait` call would be H inside an otherwise S mechanism. The required program-text coverage is complete; the absent module stream prevents an independent count of that external file under the user's frozen-token-only instruction. The program-token S total below is zero, separate from this loaded module.

## Outcomes that required judgement

**P09a/b.** Every configuration's harness uses successive queries in one process, not simultaneous execution. In AB, B waits until A stops; in BA, B reports before A starts. Tabling makes loop finitely fail; the other configurations exhaust A's budget. B nevertheless reports [3,2,1]. A's failure in P09b does not affect B=3. Budget is not treated as proof of nontermination.

**P09c.** Plain and tabling explicitly produce the full sequence and total. The other three configurations report a prefix and `freeze(Tail,gen(4,Tail))`. This is equivalent to the valid outcome, because gen(4,Tail) has exactly Tail=[4,5]; it is complete but reducible. Calling the open prefix unsound would ignore a condition that the program actually retains and can resume. There is one attributed variable and one frozen goal. The consumer runs before the producer finishes, through demand from list construction, without threads.

**P09d.** Plain/tabling reach budget while producing an open prefix, without ever binding Total or executing the consumer. Both readings are `none reported`. For coroutines/constraints/session, a residual with Total=6 and genu(4,Tail) is reported and suspended. Under the finite reading, genu has no finite least-model instance, so this residual denotes exactly the empty valid set: complete, with inconsistency undetected. It is not an unconditional finished Total=6. Under the stream reading, the tail denotes 4,5,..., giving precisely the required stream and total: complete/reduced/suspended. The special P09d1 rule about a binding during an actively running producer applies to the budget case, not to deleting a condition from this returned residual.

**P09e.** Plain/tabling report an instantiation error and no outcome. Coroutines retains two delayed equations; constraints/session retain two copies of Y+1#=X. Both are complete over all integers and reducible to one addition relation: X=Y+1 iff Y=X-1. No finite bounds are imposed. Coroutines' two delayed conditions are marked identical to the posed arithmetic information modulo control wrappers; CLPFD's normalized duplicate form is marked false, since the second subtraction has been transformed. This flag has a presentation-sensitive ambiguity: equivalent information is not necessarily an identical representation.

**P10b/c/d.** P10b stage 1 errors in plain/tabling, yet stages 2–4 are reached: replay does not run the intermediate query, and the new B is available when the standing rule is queried. Those stages are not “not reached.” Coroutines retains the directional arithmetic condition; CLPFD retains one multiplication equation. Both denote D=2*B. The remaining P10 answers agree with replacements, snapshot retention and withdrawal. P10c stage 1 is solved form: B=10 and D not yet assigned. P10d restores X=1 without reinserting the pick fact. The record shows query-time evaluation of one dependent D, not a measured proactive recomputation trace or retained history of old named values.

**P11.** All configurations have exact effects in a, and extra effects in b/c/d. One-stage emit occurs before the answer is reported (the specification's commitment point), even when it is the last goal; it is not a program deferral. The logs and timing of each entry are recorded. Reposing repeats irreversible emits, including emits on choices rejected by a replayed commitment. In P11d this leaves [1,1,1,2,3] in each non-session log, although the final query correctly fails with the committed X=1. Session's log is [1,2], and its final X=2 is unsound: stage 2 selected X=1 and stage 3 cannot validly select anew. The initial commit clause neither cuts nor stores X=v in the growing conjunction; the later stage backtracks into the earlier pick. Separate observation-run effects are excluded.

Expressibility is judged on the definitions' relation, separately from success or termination of the chosen evaluation. Thus the arithmetic mode-dispatch and replay-decoding programs are marked expressible with reformulation, with their R ranges; an instantiation error is still reported on execution. A stricter interpretation that requires every partial stage to be executable would classify some plain arithmetic cases as not expressible. The specification's separation of expressibility from operational outcome led me to the extensional definition reading used here. No finite-domain restriction or supporting solver has been credited as preserving the original domain.

## Harness and measurement findings

Six original storage records contain explicit harness faults (listed in `validation.json`). Their missing end events produce synthetic error states, which are identified as harness errors rather than native Prolog errors. There are eight differing outcome entries across those records: four BA/A entries, two readings of plain P09d, and session AB's A and B. Session AB has no B answer/end event; stage 1 was reached, but whether B itself started is unavailable, not a demonstrated B failure. No target record says a replay failed to reach a later stage. No behaviour entry has a harness fault.

Three further AB storage records (plain/coroutines/constraints) retain A's budget state but lack some boundary readings. These are unavailable measurements, not zero, and do not cause another classification difference. Other cost/storage classifications agree with behaviour. There are no target measurement reruns to substitute or compare. All original records stand.
