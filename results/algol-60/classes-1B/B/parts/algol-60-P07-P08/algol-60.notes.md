# Independent classifier B notes: ALGOL 60, P07–P08, batch 1B

I classified the public evidence independently. I did not write these programs, read another classifier's work, run an ALGOL program, run the interpreter/compiler/simulator, or use the web. The scope is the 1B P07–P08 text manifest and the corresponding batch-log runs; the brief's isolated reference to batch 1A was not used to expand that scope.

## Token decisions

The JSON uses the first path of each of the 16 texts in `TEXTS-1B-P07-P08.tsv`. The other 14 program paths inherit their text's classes. I checked the frozen token sequences of every alias against the first path. No class differs between x1 and x1sim: different execution environments do not change the role of these constructs. Token indices always come from the supplied TSVs; no program was re-tokenized. The generated line maps preserve those indices.

Rule 19 is the principal boundary. Known flags, held flags, retirement of relations, and changed-pass bookkeeping implement holding for these particular equations, so they are R. The arithmetic evaluator's assignments and fully known relation tests are P in every direction, including divisibility and zero-factor checks. The fact that an evaluator branch is not visited on these constants does not change its class. For example, `report/P07c.alg` tokens 46–51 test knownness (R), 53–62 test the arithmetic relation and record inconsistency (P), and 73–77 compute the missing place (P). Its procedure framing remains R, with nested constructs split by rule 10.

Explicit pass/order loop headers are C, as are the order dispatch in P07a and permission conditions containing definition flags in P08. Tests of which places are known remain R under rule 19. This distinguishes a holding representation from the explicit decision about when to revisit it. A possible ambiguity is whether rule 19 should absorb the entire problem-specific propagation loop into R. I applied the explicit scheduling definition of C to its header and loop framing, while retaining its problem-specific held-state operations as R. Conditions such as a failure guard beyond the relation's case test are also C under rule 2.

P07g is a harder rule 19 boundary. Computing a missing *single* multiplication place from the others is P; solving the repeated-place constraint `x*x=c1` by a square-root/sign algorithm is a changed algorithm, R. Thus proposing `entier(sqrt(c1)+0.5)`, choosing its signs and retaining the candidate list are R. Testing a fully known candidate's square against c1 is P. The sign algorithm is not a search mechanism general over relations. Its two roots exhaust this instance because `(x-3)(x+3)=0` over the integers. The use of sqrt and entier is recorded here as built-ins used in that reformulation; the explicit square check guards the candidate result on this input. These records do not establish arbitrary-precision numerical reliability of the root algorithm for unlimited constants.

The sequence constructors, decomposition, and equality operations are P by the systems file's encoding convention and rule 15. The recursive forward conc/rev cases are P by rule 3; their operation counters are H. P08c adds a three-state success/failure/missing-case protocol: its status return declaration, status locals, status assignment targets, status propagation and missing-case decisions are R, separated from the original relation applications. Permission flags and their gates are C. This is a case-specific implementation, not a general dynamic-definition interpreter.

Output adapters are H under rule 13 even when they walk a sequence or inspect held flags to print an existing state. The derived `held` count only serves observe output and is H too. No such adapter derives a missing solution. Fixed message loops, stage dispatch headers, harness-word input, unused harness-word variables, and operation counters are H under harness section 2.7. Reading a stage's constants and constructing its encoded value are P. Main block framing belongs to the harness driver. Commas and semicolons introducing the next construct follow rule 20; mixed declarations and mixed chained initialization targets are split by role rather than assigning every declared variable the same class.

## Outcomes and residual equivalence

P07a computes (5,4,3) in all six orders by deciding one relation at a time; the operation counts differ by order. P07d computes w=7 by checked integer division. P07e explicitly detects that 2 does not divide 15. P07g prints both 3 and -3, retaining them together as computed answer values. It holds no request-for-more-answers continuation, so it is finished, not alternatives pending.

P07b retains the exact conjunction, which is equivalent to x=7,y=3 but reducible. P07c retains the exact integer sum relation; its infinite set has a finite equivalent residual and is reduced by the specification's explicit example. P07f retains two contradictory sum equations; its denotation is correctly empty but the inconsistency is undetected. These are program-held flags and evaluators, not strings printed in place of state. The records' suspended classification is used even for these one-stage programs whose process then exits, consistently with the harness's stage-boundary observation contract.

P08a/b keep equality constraints rather than identifying element unknowns. At stages 4 and 5 the reversed sequence is already computed, but x=y, and later y=z, remain to be decided. They are therefore residual and reducible, not solved form. Stage 6 propagates 42 through all three element slots and reaches the explicit solution. P08c holds the application at stage 3: its enabled empty-input case does not cover (1,2), and the missing recursive case leaves it pending. Stage 4 yields (2,1). Neither a manual reapplication nor a manual intervention appears in any record.

**P08 under the closed reading is a deliberately explicit denotational decision.** I interpret the relation actually retained in the residual under each requested reading. With no rev cases, or only the empty-input case applied to (1,2), that residual denotes the empty set under the closed reading. I therefore class it complete / residual / inconsistency undetected, not an unsound explicit claim of a free b. This does **not** mean the program detected failure or adopted undefined-as-false: its printed state is pending, neither true nor false. The distinction between that operational state and the closed denotation is preserved in every entry's equivalence reasoning and observations. A competing interpretation would treat “awaiting its definition” as an assertion of future possibility rather than as a retained relation, yielding unsound under the closed reading. The problem does not explicitly settle this pending-residual case under the closed reading; I used the specification's general rule that equivalent empty residual conditions are complete even when their inconsistency is undetected, as in P07f.

Under the open reading, pending rev contributes no restriction on current values. A smaller *current-stage* representation can therefore omit that pending condition, giving a solved form with b free; at stage 3 it can also identify x with y. I mark those residuals reducible. Dropping the application would lose future work, which is a separate operational observation. This exposes another ambiguity: if “smaller equivalent” were required to preserve future resumption as well as current valid outcomes, a lone pending application could instead be called reduced. I applied the stated current-stage denotational equivalence criterion.

For residual sizes I count the primitive relation applications still undecided and unknown occurrences in those applications, alongside the cumulative input equations/applications. Definitions and already solved binding terms are recorded separately. Arithmetic compounds would be decomposed with fresh unknowns, although no surviving residual here has compound arithmetic. A named rev application counts once. `identical_to_posed` compares with cumulative posed information, not merely the most recent addition: P07b/c/f and P08c's untouched application are true; P08a/b are false after a was bound and substituted into the application. The latter convention is another possible boundary if one instead compares only the unresolved portion of the input.

The algebraic and symbolic substitution checks in `check_result.py` accompany the by-hand universal reasoning in the JSON. They manipulate mathematical values/terms only, never evaluate the submitted programs, and do not use bounded enumeration as a proof about an unbounded domain.

## Definition arrival, expressibility and supporting mechanisms

All nine configuration/program P08 combinations await **permission**, not code. The source already contains rev/conc and the case bodies. The stages set `defined`, or `concdef`, `rev1def`, `rev2def`; P08c also receives the base-fact sequences as data at stage 3. Token ranges for the compiled bodies, gates and stage updates are given in `late_definition`. A changed Boolean is not a definition body arriving. P08b leaves the permission disabled and keeps its application distinguishable from failure.

I judge each staged subproblem expressible with reformulation in each configuration: the problem-specific R representation preserves the relation's meaning, while the forward sequence cases themselves are transcriptions. This judgement concerns the staged mathematical relation, not the capability to deliver new procedure code, which these programs do not demonstrate. Hidden variants were inaccessible and were not checked; the numerical limitation of P07g above remains a limitation of the evidence. There is no evidence here of a separate variant program beyond the 30 paths in the text manifest and batch log.

There are **no S mechanisms and no S tokens** in any of the following programs, in each of report (`.alg`), x1 (`.a60`) and x1sim (`.a60`): P07a, P07b, P07c, P07d, P07e, P07f, P07g, P08a, P08b, P08c. Consequently `s_mechanisms` is empty. Phase 4 lists none supplied. The programs supply specific equation holders, element-equality holding, a pending-rev flag and (in P08c) case-availability status, all R rather than a reusable general relation store, unifier, loader, or scheduler. The broad example “wait-for-definition layer” in the S definition is potentially ambiguous here; I use rule 19's more specific distinction by generality. I would classify a general reusable loader/dispatcher as S. Report's IFIP input/output calls are external mechanisms per the systems file, classed here as H for harness input/output and P for stage constants; x1's corresponding procedures are its own core I/O.

## Record coverage and access

There are 45 behaviour records with 75 physical stages. P08 stages are recorded twice, with `reading` closed/open, producing 114 outcome entries. All 60 original cost/storage records (100 stages) were compared against the matching behaviour run. The verbatim answers, observed state, printed stage output and execution classifications agree, so `mode_differences` is empty. No P07–P08 raw-rerun-m2 records, INVALID records, harness faults, limits, errors before stage end, or unreached stages are present. `rerun-m2-log.tsv` does not exist in this clone. Null/unavailable measurements were not converted to zero. Zero suspended/resumable work stated from the program's observed state is distinct from an unavailable storage measurement.

Report/x1's budget process recreates earlier stages as documented, despite the incremental posing label. That is recorded in observations, not called manual intervention. x1sim receives P08 stages into a live process. Exhausted-input errors after an emitted [end] are documented harness shutdown and do not change the completed stage to error. No earlier explicit no-solution conclusion is withdrawn; under the closed interpretation the mathematical valid set changes when the definition becomes available, but the program had only printed its pending state.

Files read were confined to the allowed evidence: the five root specification/protocol files; the permitted problem files; systems/algol-60/README.md; the harness README, ALGOL README, S-mechanisms and relevant QUESTIONS text, stages.json and record.schema.json; the report P07/P08 program sources inspected above; all three configurations' P07/P08 constants; the batch text manifest and corresponding frozen token TSVs (including aliases); the 105 P07/P08 raw JSON records; and batch-log.tsv. Directory/file inventories were confined to allowed directories. Files generated in this output directory were also read for checking. **No file outside the permitted list was read, and no prohibited evidence was encountered accidentally.** One validation command accidentally wrote a JSON copy to `/private/tmp/algol-60-P07-P08-validated.json`, outside the requested output directory. I removed that copy immediately without reading it. This was a write-location mistake; all deliverables and checking scripts are in the requested output directory. In particular, the source repository was not modified, and no author README/audit, other classifier's classes, earlier batch results, variants, calibration, reviews, transcripts, other system directories or external files were opened.
