# Classifier A: absys, batch 1B (P04, P06, P07, P08). Notes

Classifier A, a Claude agent (claude-opus-5-5), working on the clone at
commit b73d59a. `absys.json` is generated by `build.py` in this folder
(`python3 -I build.py REPO OUTDIR`). The build checks that every token of
every text is covered exactly once, and that each stage's execution state
as classed agrees with the record. Other scripts here: `summ.py` and
`compact.py` (read records), `cmpcfg.py` (compares configurations),
`cmpmode.py` (compares modes with the behaviour run), and `check_p08a.py`
(residual equivalence for P08a, stages 4 and 5).

The brief's file name says P04, P06 and P08, but its text names P07 as well,
and `TEXTS-1B-P04-P06-P08.tsv` lists the P07 texts. I classed all four
problems.

## Tokens

30 texts and 1436 tokens. Every text is shared by the three
configurations, and no class differs between them: no configuration has
an S mechanism, and the programs contain no configuration-specific
construct. So each text is classed once, under its `absys/` path.

Hard or debatable constructs:

1. **The constants block** (`% CONSTANTS BEGIN` … `END`). The harness
   never gives it to the system. It substitutes each value into the
   section that uses it. Its lines are not comments, so the tokenizer
   counts them. I classed them **P** (rule 1): they are the information of
   each stage, and they are the only place a value appears. They are not
   H: harness README 3.12 says only `tout("emit", …)` is H. Someone else
   could reasonably argue for H, since the harness reads the table. If
   they did, the P totals would fall by about 25% in P06e and P07.
2. **P08c, `revmore`** (R tokens 77–83, 86–92 and 116; 15 R tokens in
   all). The program gives rev at stage 3 as case 1 *or* `revmore(p, r)`,
   and defines `revmore` as case 2 at stage 4. I classed the alternative
   `or revmore(p, r)` as R, because it is a case the problem does not
   give; the `or` goes with it by rule 20. I classed revmore's head
   (`revmore=lambda p, r begin`) and its closing `end` as R by rule 4.
   Case 2's contents (93–115) are P by rule 10. The `{`, `}` and `end` of
   rev's own definition are P. **Possible anticipation:** the stage-3 code
   names a procedure for cases "not yet given", so it presumes that more
   cases may come. The problem's open reading itself says "case 2 may yet
   arrive", and the program does not depend on what stage 4 contains. So I
   do not count it as a breach of rule 5, but I flag it.
3. **P08c.redefine** (named variant). It is all P: each stage's part of
   the definition is transcribed literally. It changes the meaning
   because Absys treats a definition as an equation on a name. No token
   does it.
4. **P06d.set** (named variant). I classed the set former as P by rule 7,
   which P06d permits. It is not equivalent to the problem's setdiff for
   an s1 with repeated elements, or for one whose order differs from the
   order of its derivations. That matters for hidden variants, not for
   the class.
5. **P07a in six orders.** Each order is an instance the problem poses,
   so it is P and not a move (rule 4). The `begin … end` grouping is P, as
   the conjunction connective. The compound `x + y + z = 12` is a
   transcription (SPECIFICATION, Conventions).
6. **P06e facts as procedures** (`student = lambda P {P = st1} or {P =
   st2}`). P by rule 6: a set of facts the problem states, in a closed
   world. I gave each `or` between facts to the following fact (rule 20).
7. **P06d mem, case 1: `S = [E|T]`.** Here T ranges over every value,
   where the problem says "for every sequence t". This makes no difference
   on the inputs used. I classed it P as a transcription, but it is a
   (harmless) widening.

## Outcomes

There are 138 stage entries: 46 stages in each of the 3 configurations
(30 programs in each, the 2 named variants included). There are no
`*.INVALID.json` records and no harness faults. Every stage was reached.
The other two configurations print the same state as `absys` (up to the
numbering of derivations) except in **P04a under absys-depth-first**
(`cmpcfg.py`).

Hard cases:

1. **P04a, absys-depth-first.** Both derivations were still elaborating
   at the budget. Derivation #2 holds `x = 1` still *to do*, and `? x`
   says "x does not occur". I classed it as *complete / residual /
   reducible*, identical to the posed information, with *budget*. The
   reasoning: it is state the system holds and would act on, observe()
   reads it, and the specification's examples (P07f) count held, posed
   relations as reported. **Alternative:** *none reported*, since no
   binding of x is held at all. I expect a dispute here. Either way, the
   finding stands: depth-first, the endless alternative stops x = 1 from
   being taken up.
2. **P04a and P04b under absys and absys-wake-back.** These are classed
   *explicit* on x = 1, with *budget*. The other derivation, still
   elaborating `loop(x)`, denotes nothing under the least relation. I
   recorded it as an observation (SPECIFICATION, Outcomes 2: the more
   explicit valid form).
3. **P04d and P04f.** In every configuration the behaviour run is
   *error*: the kernel sent SIGKILL for lack of memory after about 3
   seconds. So nothing was reported, and the record cannot say whether
   every solution would eventually be reached.
4. **P06a and P06c, stage 1** are *unsound*. `not(x = 1)` is decided at
   once, at step 5. Its independent computation binds its own x to 1 and
   finds no contradiction, so the `not` fails, and no derivation survives.
   So decisions.md rules 18 and 19 ("waits") do not make this negation
   wait: it is negation as failure without a floundering check. P06a stage
   2 stays unsound. P06c stage 2 is *complete*, but only because the run
   had already failed.
5. **Empty reports.** I gave "no derivation survives" the representation
   *explicit*: the empty set of solutions, given as such. The
   specification has no class for this case, and others may use null.
6. **P07b residual** (`x + y = 10; 4 + y = x`). I flagged it as identical
   to the posed information, because the system only rewrote x − y = 4 in
   additive form and decided nothing. Someone could say *false*, on the
   grounds that it was rewritten.
7. **P08 under two readings.** `semantic` is a string ("open: …; closed:
   …"), with `semantic_open` and `semantic_closed` added as separate
   fields. At P08a stages 4 and 5, the unknowns are held as chains of
   suspended equations between unknowns, through auxiliary h₁…h₆. I
   classed that as *solved form* (identifications), checked equivalent by
   `check_p08a.py`, with the execution state *suspended*, as the harness
   gives it.
8. **Mode differences.** The only differences are in P04d and P04f, in
   every configuration. The cost and storage runs end in *timeout* (two
   attempts, 60 s and then 600 s). The behaviour run ended in *error*. The
   m2 reruns end in *error*, like the behaviour run. The semantic result
   is the same in all of them (none reported). Every other cost and
   storage stage matches its behaviour run.

## Rules I find ambiguous

- How to class the constants block: the brief does not say, and neither
  do METRICS or the harness README.
- When a held but untouched disjunct counts as "reported"
  (SPECIFICATION, Outcomes 2): the P04a depth-first case.
- The representation of an empty report.
- Whether a suspended equation between unknowns is still *suspended*
  work once the result is in solved form.
- Rule 5 (no anticipation) against a reformulation that names "cases
  still to come" (P08c).
- `batch-log.tsv` has interleaved and truncated lines around these runs,
  which looks like concurrent writes. I counted runs from the raw records
  instead: 90 behaviour records, matching every program and configuration.
