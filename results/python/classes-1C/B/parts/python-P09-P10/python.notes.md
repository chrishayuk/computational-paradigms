The difficult construct boundaries were these:

- **Arithmetic evaluators in P09e.** `plus`/`minus` arithmetic and fully known relation tests are P in every direction, including branches not reached in these runs. Tests for which places are known, and the return that says to wait, are R by rule 19. The returned tuple containing computed arithmetic remains P under rule 10. Treating the entire evaluator as R, or only the actually executed branch as relevant, would contradict rule 19’s clarification.
- **Problem-specific holding versus general supporting code.** Core P09e’s `place`, fixed `EVALUATOR` and `decide` operate on this problem’s two arithmetic relations; I class their holding machinery R. Stdlib P09e uses the same fixed arithmetic representation, adding C for thread creation, locks, notification and settling. P10b holds only its standing multiplication dependency, and P10d holds only its pick/comparison information; that holding/recovery is R, with C for control and store clearing. In contrast, stdlib P09c/P09d’s dispatcher accepts relation names and arbitrary places, installs arbitrary returned bindings and launches arbitrary returned body goals. It implements a reusable dataflow scheduler, not just calls to the external threading library. Its implementation is S under rules 12/19. This boundary is a substantive judgment: all these helpers could be reused after edits, but only the latter interface supports new relation implementations without changing the dispatcher’s work.
- **New S adapters in extended.** `Goal` holds an arbitrary relation callable and its arguments, interprets failure/wait verdicts and resubmits it. `Relation` similarly adapts an arbitrary arithmetic evaluator to Vars, waiting and binding. These general mechanisms are S, not automatically P because the class is instantiated with a problem relation, and not part of the phase-4 queue. Their `__repr__` methods are H output adapters. The imported phase-4 mechanisms are listed with their full published frozen sizes; imports and their scheduling directives are C call-site constructs, not copies of those implementations.
- **Unification and resolution.** Extended P09a’s general `unify` is S (no occurs check), as are `children`/`done`, which implement leftmost goal-list resolution. The concrete loop/conc/rev cases are P, including case-head equality tests and construction/decomposition of their cons encoding. Calling search is C; the nested problem query remains P (rules 2, 10, 15). None of these original inputs creates a cyclic term.
- **Reporting versus deciding.** Pure `show`, `Shown`, encoding printers and loops printing precomputed candidate values are H under rule 13. Tests and traversals that establish whether a conjunction/current result exists are classed separately as R. A test that interprets an initialized empty candidate set as a no-solution conclusion is R; the actual failure message and printing of candidates are H. There is an unavoidable edge here: a printer often tests availability, but a test needed to establish a semantic conclusion is doing more than rendering it. I have exposed that edge rather than counting every `report` helper wholesale as H.
- **Retraction.** Time/stage tags, saved information, trail marks and reconstruction are R: they add a representation and recovery algorithm. Clearing reusable candidate/waiting storage, or undoing the store’s trail, is C (rule 16); restoring the domain’s meaning is observed separately. The primitive pick membership test is P under rule 9, and `>` and multiplication in the directions used are P. `in` hides pick’s individual fact tests from problem-operation counts; this use is explicitly listed here.
