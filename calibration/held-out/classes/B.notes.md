# Classifier B notes

I used only the brief, required specification/protocol/core files, the two programs, their fixed token TSVs, the ALGOL input, and the recorded outputs. No other classifier's work was consulted. Token indices are the supplied indices; no retokenization was performed. Every Python index 0–1572 and ALGOL index 0–1872 is covered once. Nonresidual outcomes have `simplification: null` (not applicable).

Hard token boundaries:

- **Arithmetic evaluators versus rule 19.** I distinguish the primitive relation's arithmetic from the implementation's decision about whether enough values have arrived. Arithmetic checks and bindings in r1/r2/r3 and rel1/rel2/rel3 are P under rules 3 and 8; zero and divisibility tests enforce the integer relation, rather than imposing search policy. Known-value dispatch and waiting verdicts are R under rule 19. Returning a verdict or setting its binding fields is taken as the local representation of the primitive result. The `known` argument packages the problem's unknowns; I did not count it as an extra efficiency argument under rule 5. This is the hardest interpretation: rule 19 could be read to absorb the entire evaluator, while rules 3/8 could be read to absorb its mode dispatch. The rules do not explicitly settle that boundary. Nor is it completely clear whether the primitive's unused mode branches count as directions outside the queries under rule 3; I treated the evaluators as direct implementations of the integer primitives, whose places may be unknown (SPECIFICATION.md, Arithmetic and comparison).
- **Problem-specific resumption.** Retaining bindings, arrival order, liveness and dependencies, and repeatedly taking up held relations is R under rule 19, rather than S. These mechanisms dispatch only this problem's three relations. I give rule 19 priority over the general C description for their loop/dispatch machinery. A reusable constraint engine would be S. The rules should explicitly state how rule 19 interacts with C scheduling and nested primitive evaluations.
- **Derived finite solver.** The combined R1/R2 calculation is R (changed algorithm, rule 3), including the applicability checks embedded in report. Generating candidate divisors and their signs is C under rule 6, with nested arithmetic R under rule 10. This is not a separately written reverse direction of one defined relation (rule 14); it is a new combined algorithm. The positive/negative enumeration is not a list of the problem's stated facts. Rule 14's word “throughout” could otherwise conflict with nested C/H constructs.
- **Report is not wholly H.** Pure formatters, trace collection and examination counters are H under rule 13. Calls that derive the finite solutions, and the state analysis selecting that solver, are R. In ALGOL the two computed expressions inside outinteger calls are R, while the call/formatting shell is H. Signed divisor s itself is already computed and its printer is H. This applies the adapter exception at argument granularity (rule 10). The combined solver's n counter calculates the reported solution count and is R; the examined counters merely measure work and are H.
- **Stages and wrappers.** Literal stage constants and the Python arguments expressing prescribed stages/orders are P; harness iteration and labels are H. All six prescribed orders are part of P02b, so iterating them is not an unstated C enumeration. Reading input is a pose stand-in (H), whereas inserting it in the held relation store and resuming it is R. The ALGOL per-run resets reuse store (C, rule 16); observation-only resets are H. Whether a new-run reset changes the next run's computed values makes rule 16 less clear than its categorical wording suggests.
- **Punctuation/layout.** Separators take the following construct's class (rule 20), including commas introducing P stage arguments and semicolons before changes of role. Closing blocks/layout belong to their opening construct (rule 10). A construct can consequently have multiple spans around nested constructs. Rule 20 does not specify terminal semicolons or layout explicitly; I use the enclosing construct for terminal punctuation.

Outcome reasoning, identical for both programs:

- Every one of the 22 stage reports is complete against P02's valid-outcome tables. R1 alone denotes exactly u+v=16, w free. R2 alone denotes exactly w*u=v. R2 with R3 denotes u=2 and 2*w=v. Each is a genuine retained residual that the next stage acts on, not merely an echo (SPECIFICATION.md, Outcomes 2).
- Those residuals are reduced: each has one primitive relation and the necessary unknown occurrences. In particular v=2*w is still a multiplication relation; arithmetic expressions are not solved-form terms under Outcomes 2, so the R2/R3 stage stays residual. Integer domains are supplied by P02 for all unknowns.
- R3 alone and R1/R3 yield solved forms with the remaining integer unknowns free. All three relations yield the explicit unique triple (2,14,7).
- For R1/R2, eliminating v gives u*(w+1)=16. The nonzero signed divisors of 16 are exactly ±1, ±2, ±4, ±8, ±16. The programs report (d,16-d,16/d-1) for all ten, with no duplicates or invalid triples. This establishes complete/explicit at P02a stage 2 and the corresponding two P02b stages. Although the live residuals are also shown as observations and retained internally, the report actually enumerates every solution, so I classify its answer representation as explicit. The specification does not explicitly say how to label a report that contains both an explicit enumeration and the equivalent retained residual; that ambiguity should be clarified.

No rule needs changing solely to obtain particular totals; the boundary ambiguities above warrant clarification before freezing.
